# Supported harness interface audit — 29 October 2026

This is an interface and admission audit, not a paid comparative evaluation or a claim of identical execution guarantees. Research used official upstream documentation and installed executable/package metadata. Existing authentication stores were not opened. No software was installed, no login was performed and no inference request was made.

## Pi

The maintained upstream is now [earendil-works/pi](https://github.com/earendil-works/pi). Its coding-agent package is [`@earendil-works/pi-coding-agent` 1.4.0](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/package.json), under the [MIT license](https://github.com/earendil-works/pi/blob/main/LICENSE). The installed managed package was also 1.4.0. Firik admits this exact audited version; other versions are unavailable until their protocol and security flags are revalidated. Users install and maintain their trusted runtime separately. Firik neither vendors it nor executes an installer.

The official [RPC interface](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md) is bidirectional LF-delimited JSON on stdio. Commands have correlated request IDs; events continue after prompt acceptance. `agent_end` is not completion because automatic work can follow. The adapter waits for `agent_settled`, requests `clear_queue` then `abort` on cancellation, and closes stdin for orderly disposal before terminating a hung process group. It never automatically reconnects or resubmits an uncertain request.

The [command reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc-commands.md) exposes model/provider state, prompts, cancellation and context inspection. Firik checks the actual exact model and provider before submitting the prompt and rejects changes. Only explicit supported provider API keys handed to the adapter are admitted; no existing OAuth/auth file or ambient API key is imported. Supported provider selectors are `openai`, `anthropic` and `google`, through their documented environment variables. `allow_live: true` and provider-network permission must both be explicit. They authorize inference only, and do not give model output authority to execute tools.

The [CLI reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md) documents the tool/resource/configuration controls used by this adapter. Every process starts with all tools, extensions, MCP, skills, templates, themes and context discovery disabled, project trust denied, ephemeral session storage and offline catalog behavior. The process receives a fresh empty cwd/home/config/cache directory. No project files, MCP configuration, shell, plugin or user home are passed. An observed tool or extension execution event fails the run and stops the child. External prompts are therefore suitable only for explicitly supplied non-sensitive content. The trusted installed runtime remains a host process with ordinary OS rights; **this is not a sandbox**. Requests for filesystem admission, coding tools, host approval enforcement, a required sandbox or a hard token budget fail closed.

The [event reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/json.md) defines text deltas, authoritative assistant messages, tool/retry/compaction events and reported cumulative usage. Final assistant messages replace partial text. Duplicate final messages are deduplicated before usage aggregation. Identified duplicate events are suppressed; unidentifiable text deltas cannot reliably be distinguished from repeated legitimate text. Missing usage remains unknown. Pi price-derived costs are not invoices, so the adapter leaves monetary cost unknown. Backend completion is unverified until an independent host evaluator provides evidence.

## Codex

Codex has an official [SDK and app-server](https://developers.openai.com/blog/codex-as-a-platform), rather than requiring an unofficial login wrapper. Its source is [Apache-2.0 licensed](https://github.com/openai/codex/blob/main/LICENSE). A local Codex executable was found; its authentication and personal configuration were not read. No supported execution version is claimed by Firik.

The official [app-server reference](https://developers.openai.com/codex/app-server) documents `initialize`/`initialized`, thread lifecycle, `turn/start`, streamed item/plan/diff events, `turn/interrupt`, status, token usage and approvals. It also documents restricted read roots in newer sandbox policies, while default `readOnly` grants broad read access. These are version-sensitive protocol capabilities, not proof that a particular installation's whole runtime, config loading, integrations or native tool execution obey Firik's narrower policy. An API key or legitimate explicit OAuth authorization would be needed for model access; Firik does not copy installation credentials. Platform sandbox enforcement and process cleanup require separate runtime validation.

`CodexBackend` is deliberately unavailable. It implements the common lifecycle surface with a clear admission error and unknown capabilities. It does not launch an unrestricted shell command, synthesize success, claim inherited approvals, inspect credentials, or silently substitute another backend. A future admission needs version-generated schema checks, private configuration, an enforceable whole-runtime scope, a sandbox/approval mapping and real platform escape tests before any task is dispatched. Restricted-read protocol documentation alone does not satisfy that gate.

## Other suitable open-source interfaces

[OpenCode's official SDK](https://opencode.ai/docs/sdk/) exposes typed server/session APIs, event subscriptions and cancellation; its server starts locally and supports client-only attachment. Its documentation explicitly says server startup still consumes existing configuration. The [official source](https://github.com/anomalyco/opencode) is maintained and the [SDK license](https://github.com/anomalyco/opencode-sdk-go/blob/main/LICENSE) is MIT. This is a credible future integration candidate, but Firik has not admitted a version or mapped its filesystem/tool permissions, credentials, plugins, server authentication and cancellation to the host boundary. It is not advertised as an available backend. The source project's license and all redistributable components must be reviewed for the exact version if vendoring is later proposed; no dependency code is bundled here.

## Security and validation limits

The external process transport uses argv execution, an environment allowlist, LF-only framing, bounded frames/queues/text/diagnostics, deadline enforcement and explicit disposal. Raw protocol records are treated as untrusted. Error codes, sanitized messages, exit state and bounded diagnostic details survive normalization. Sessions are owned by a backend instance and project identity, with at most four simultaneous Pi sessions and one task per session; no state transfer or backend switch occurs mid-task. Temporary directories are removed on explicit close. Process-tree cleanup is supported on POSIX and is best effort against trusted-runtime failures; deliberate process-group escapes are not confined. Windows external dispatch is disabled because Job Object containment is not implemented.

Offline tests execute small fake protocol processes, covering fragmented JSONL, Unicode separators, malformed/truncated frames, duplicates, unexpected tool activity, unknown usage, crash, cancellation, hung-process cleanup, event overflow, environment isolation, session ownership and model mismatch. They establish adapter behavior, not live Pi provider compatibility or an OS security boundary. Real provider execution remains opt-in and requires explicit credentials and authorization. Codex, OpenCode and cross-provider paid rankings have no implementation-run evidence.
